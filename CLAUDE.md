# CLAUDE.md — BetPredictor (personal football value-betting engine)

You are building a **personal, local-only** tool that predicts football
Asian Handicap (AH) and Over/Under (O/U) outcomes with a statistical model,
compares them with SportyBet (Nigeria) odds, builds daily slips, generates
SportyBet booking codes, and tracks results.

Read this file fully, then read every file in `docs/` in numeric order
**before writing any code**. The docs are the specification. If the docs and
your instincts disagree, the docs win. If the docs are silent or ambiguous,
**stop and ask the user** instead of guessing.

---

## 1. Non-negotiable rules

1. **Never place bets.** The system only produces booking codes. There is no
   login, no account, no stake submission, no payment code anywhere. Do not
   add any, even if it seems convenient.
2. **Never invent external endpoints, market IDs, selectors or column names.**
   Everything about SportyBet, Understat, and football-data.co.uk must be
   *discovered and verified* against live responses first (see
   `docs/04-sportybet-integration.md` and `docs/02-data-pipeline.md`).
   Record every discovered fact in `docs/discovered/` with the date and a
   sample payload before code depends on it.
3. **Phase gates are hard gates.** Work in the phase order in
   `docs/08-phases-and-acceptance.md`. Do not start phase N+1 until every
   acceptance check of phase N passes and you have shown the user the output.
4. **No silent failures.** Every scraper, fit, and job logs structured errors
   and writes a row to `job_runs`. Never `except: pass`. Never drop rows
   without counting and logging how many and why.
5. **Cache raw data.** Every HTTP response used for ingestion is saved under
   `data/raw/<source>/<YYYY-MM-DD>/` before parsing, so parsing bugs can be
   fixed without re-scraping.
6. **Be polite to websites.** Respect the rate limits in `config/settings.toml`.
   Randomised delays, a single worker, a normal desktop user agent, no
   parallel scraping. If a site returns 403/429, back off and stop; do not try
   to evade blocks.
7. **Time is stored in UTC**, displayed in `Africa/Lagos`.
8. **Money maths uses decimal odds** everywhere. Never American or fractional.
9. **Tests before trust.** Every mathematical function listed in
   `docs/03-model.md` and `docs/05-value-and-slips.md` has table-driven unit
   tests with the exact cases given there. Those tests must pass unchanged.
10. **Paper mode is the default.** Slips are logged as `paper` unless the user
    marks one as `placed` in the dashboard.

## 2. Tech stack (fixed — do not substitute)

| Layer | Choice |
|---|---|
| Engine language | Python 3.12, managed with `uv` |
| Numerics | numpy, scipy (`scipy.optimize.minimize`, `scipy.stats.poisson`), pandas |
| DB access (engine) | SQLAlchemy 2.x ORM + Alembic migrations |
| Config | `pydantic-settings` reading `config/settings.toml` + `.env` |
| HTTP | `httpx` (sync client is fine) with `tenacity` retries |
| Browser automation | Playwright for Python (Chromium) |
| Local API | FastAPI + uvicorn, bound to `127.0.0.1` only |
| Tests | pytest, pytest-cov |
| Lint/format | ruff (lint + format), mypy (strict on `engine/src/engine/model` and `engine/src/engine/value`) |
| Database | SQLite, single file `data/betpredictor.db`, WAL mode |
| Dashboard | Next.js (App Router, latest stable), TypeScript strict, Tailwind CSS, shadcn/ui, Drizzle ORM with `better-sqlite3`, Recharts |
| Task runner | `Makefile` at repo root |

**Schema ownership:** Alembic (Python) is the *only* thing that creates or
alters tables. The dashboard reads the DB through Drizzle using schema types
generated by `drizzle-kit pull`. The dashboard **never writes** to the DB
directly; every write goes through the FastAPI engine (see `docs/07-dashboard.md`).

## 4. Makefile targets (must exist and work)

```
make setup        # uv sync, playwright install chromium, pnpm install, alembic upgrade head
make migrate      # alembic upgrade head
make ingest       # football-data.co.uk history + Understat xG
make map-teams    # run team-name resolution, print unresolved names
make fit          # fit models for all enabled leagues
make backtest     # walk-forward backtest, writes backtest_runs + report
make discover     # SportyBet endpoint/market discovery (interactive, headed browser)
make odds         # fetch upcoming fixtures + AH/OU odds from SportyBet
make picks        # predictions -> value legs -> slips
make book         # generate booking codes for today's unbooked slips
make close        # snapshot near-kickoff odds for CLV (run ~30-60 min before kickoffs)
make settle       # fetch results, settle legs and slips
make daily        # ingest -> odds -> picks -> book  (the normal daily command)
make api          # FastAPI on 127.0.0.1:8765
make dashboard    # Next.js dev server on localhost:3000
make dev          # api + dashboard together
make test         # pytest + dashboard typecheck + lint
```

## 5. How to work

- Implement one phase at a time; within a phase follow the task order.
- After each task: run `make test`. Fix before moving on.
- At the end of each phase: run its acceptance checks, paste the outputs to
  the user, and wait for approval.
- Keep functions small and pure in `model/`, `value/`, `slips/`. All I/O lives
  in `ingest/`, `sportybet/`, `settle/`, `db/`, `api/`.
- Every tunable number lives in `config/settings.toml`. No magic numbers in code.
- When something external differs from these docs (a column renamed, an
  endpoint changed), update `docs/discovered/`, tell the user, and adapt the
  adapter layer only — never the model or maths.

## 6. Honest framing (keep in UI copy and reports)

No model can guarantee wins. Bookmaker odds are efficient; the purpose of this
system is to find *small positive expected value* and to **measure honestly
whether it exists**. The backtest gate in `docs/08` and the paper-trading
period exist for that reason. Never label anything "sure", "guaranteed" or
"fixed" in the UI.
